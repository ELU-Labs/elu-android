# 0.2.1 release decision

Date: 2026-11-03. Artifact: `dev.elu:elu-analytics:0.2.1`.

## Decision

Release 0.2.1 with the replay, delivery and configuration fixes listed under
[Changes since 0.2.0](#changes-since-020). The public API is the same as in
0.2.0: `baselines/current/api/public-api.txt` is unchanged.

After 0.2.1 is published on Maven Central, ELU's service configuration enables
native session replay for Android installations. The service selects native
replay by platform, not by SDK version, so installations on 0.2.0 and on 0.2.1
get replay at their next configuration renewal when their project has replay on.
Publishing 0.2.1 does not by itself enable replay; the enablement is a service
change and is not part of this artifact.

0.2.1 is released on the checks listed below. Of the checks 0.2.0 deferred:

- replay privacy on device, `FLAG_SECURE` windows and an upgrade in place ran
  before publication ([Deferred checks that ran](#deferred-checks-that-ran));
- end-to-end replay read back from ELU's production service, and playback in
  ELU's replay player, run after the service enables Android replay. Their
  results are added to this file then
  ([After Android replay is enabled](#after-android-replay-is-enabled));
- performance overhead is waived ([Waived](#waived)).

## Scope

- Only `dev.elu:elu-analytics` is published. The optional
  `dev.elu:elu-analytics-compose` module stays in this repository and is not
  published.
- 0.2.1 opens a 0.2.0 store in place. The owned SQLite schema is unchanged, so
  identity, consent, queued events and queued replay chunks are kept. Replay
  chunks that 0.2.0 queued keep their `[masked]` form and are still delivered.
- 0.2.1 does not import data stored by 0.1.0, as for 0.2.0.

## Changes since 0.2.0

From `git log 0.2.0..` on the release commit:

- **Star masking** (#27). Masked text and input values are encoded as one `*`
  per character, keeping spaces and line breaks in masked text, instead of
  `[masked]`. Touch samples over text made only of `*` and whitespace are
  refused.
- **`FLAG_SECURE` windows** (#24). A secure window is recorded as one
  "Content hidden" placeholder with no layout, text or touches, checked again on
  every capture. A pass during which the window becomes secure is discarded.
- **SurfaceView and TextureView** (#26). Both are encoded as placeholders.
- **Views replay `409`** (#25). A `409` on a Views replay chunk, even with a
  validated identity-conflict body, holds the chunk instead of stopping it: the
  same bytes are offered again after one hour to one day, until the chunk
  expires. A chunk that 0.2.0 stopped after a `409` becomes a hold on its first
  claim after the update. Declared-region `409` and `413` stay final.
- **Calls during the foreground configuration fetch** (#25). Calls made after
  the app returns to the foreground, until the new configuration arrives, are
  held under the launch rules (100-call cap, consent rules, call-time
  timestamps) and recorded when it arrives. 0.2.0 discarded them, including the
  `Application Opened` and screen events of every return to the foreground.
- **Held chunk and a forced re-check** (#22). A stop behind a held or refused
  chunk is recorded before the next replay attempt, so a forced re-check cannot
  start a second recording in the same session.
- **Retained crash report** (#21). A withdrawal that races an intake update no
  longer deletes a retained automatic crash report.
- **One-platform declared-region grants** (#29). A grant whose `platforms` list
  names one platform is accepted. A list that names only `ios` keeps the base
  configuration without declared-region replay. 0.2.0 dropped the whole
  configuration for either one-platform list.
- **Tests only, no behaviour change:** real-pipeline and iOS-parity replay
  privacy instrumentation tests (#26), identity calls while opted out, disabled
  or region-blocked (#28), bounded main-thread waits in the instrumentation
  tests (#23) and the root-replacement test fixture (#20).

## Required before publication

1. The release commit is reviewed and merged to `main`, and its CI run on
   `main` passes every job: unit tests, lint, instrumentation tests on the
   API 23, 29, 35 and 36 emulators, the minified consumer apps run on each of
   those emulators, the public API snapshot, brand and legal artifact scans,
   local distribution checks, the coordinate-only consumer builds (R8 full
   mode with compileSdk 36 and 34, OkHttp 5, Java only, Kotlin 2.0 and
   Compose) and the historical 0.1.0 consumer build.
2. A consumer app built with the core AAR from that CI run is checked end to
   end against the ELU service. Replay is off for this check, because the
   service enables Android replay only after publication. Read back from ELU's
   event store: configuration fetch, custom events with device and app
   context, screens, identify and person properties, feature flags, and these
   three delivery legs:
   1. **Restart delivery.** Events queued while the device is offline, with
      the app process killed and relaunched while still offline, are delivered
      after the network returns, with no duplicates.
   2. **Launch-time calls.** Calls made at app launch before the first
      configuration arrives are delivered after it arrives, in call order and
      with their call times.
   3. **Kill before configuration.** Calls made before the first configuration
      arrives are lost when the process ends before it arrives. This is the
      documented behaviour (README "Setup", CONTRACT.md). The leg records that
      loss and that the next launch works normally; the loss is expected, not a
      failure.

   The signed tag message records the outcome of each leg.
3. An annotated OpenPGP-signed tag `0.2.1` from a trusted release key, with the
   trailers listed in [release/README.md](../README.md), names that CI run and
   that AAR's SHA-256.
4. The release workflow passes as a dry run, then runs for real. It rebuilds
   the AAR byte for byte and uploads only the core artifact, without releasing
   it. A maintainer checks the deployment in the Central Portal and clicks
   Publish.

## After Android replay is enabled

These run against ELU's production service once it enables native replay for
Android. Each result is added here with its date.

1. **Replay end to end, 0.2.1.** A probe app built with the published 0.2.1
   AAR, with replay on: native replay selected, replay chunks stored and
   accepted, each recording's chunk sequence complete with no duplicates. In
   the stored recording the readable label is present, the typed input and the
   `maskView` text appear only as `*` of the same length, `blockView` and
   `WebView` content appear as "Content hidden", and no `[masked]` token
   appears.
   - Result: not run yet.
2. **Replay end to end, 0.2.0.** The same with the probe app built with the
   0.2.0 release AAR, which also gets replay.
   - Result: not run yet.
3. **Upgrade in place, 0.2.0 to 0.2.1.** The store is kept, the analytics
   session continues, a new replay ID starts, and no chunk is lost or sent
   twice.
   - Result: not run yet.
4. **Playback.** An Android recording plays in ELU's replay player with the
   privacy result of item 1.
   - Result: not run yet.

## Waived

- **Performance overhead** (CPU, memory and frame time with replay on): waived
  for 0.2.1 by the release owner, as for the iOS SDK.
- **Physical devices:** the checks above run on emulators only, as for 0.2.0.

## Release notes must say

- Session replay for Android: ELU turns it on per project, and it needs
  Android 10 or later. Masked text and input values appear as `*` characters
  of the same length. Images, WebViews, Compose content and blocked views
  appear as "Content hidden" placeholders, and a `FLAG_SECURE` window as one
  placeholder.
- Use the site key of the ELU project for the app; replay follows that
  project's settings. Drop the 0.2.0 note about keys from projects with iOS
  replay.
- Upgrading from 0.2.0 needs no code changes.
- The Compose add-on is not published.
- A link to this record.
